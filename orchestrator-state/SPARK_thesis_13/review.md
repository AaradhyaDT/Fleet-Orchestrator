# SPARK thesis evidence review

**Scope:** Read-only adversarial audit of the two scout reports against the checked-in SPARK sources and saved artifacts. I did not run notebooks, train models, or alter SPARK. Findings are grounded in [[SPARK]] and [[Human fall detection]].

**Citation convention:** Source paths and line numbers below are relative to the SPARK repository root.

## Verdict

The repository supports a **SisFall offline human-fall classification result**, not a validated wearable or clinical system. Use the saved result artifacts as *reported artifact measurements* (not independently reproduced measurements), keep model generations separate, and make all threshold, sampling, cohort, firmware, and power limitations explicit. Human fall detection is the primary thesis scope; robotics is exploratory future work, not evaluated here (`README.md:5`; `docs/SPARK_Proposal/Chapters/chapter6_expected_output.tex:50-55`; `docs/SPARK_POST_BOARDS_MASTER_PLAN.md:14`).

## Approved thesis claims, with qualifications

| Claim safe to retain | Evidence classification and required wording |
|---|---|
| Processed SisFall model input is 200 samples × 6 IMU channels at 100 Hz (2 s). | **Artifact/code-supported input contract.** Preprocessing downsamples native 200 Hz data to 100 Hz and defines a 200-sample window; training loads `(N, 200, 6)` (`training/data_prep/prepare_sisfall.py:8-14, 26-32`; `training/train_cnn.py:65-68`; `AGENT.md:11`). |
| A saved held-out SisFall report gives 0.8781 sensitivity and 0.9185 AUC at a validation-selected Youden threshold of 0.3919. | **Stored artifact result, not re-run here.** Attribute it to that report and its test set of 6,712 windows / 8 subjects; specificity is 0.7818, so do not imply the 90% sensitivity and specificity targets were met (`data/processed_sisfall/model/test_report.txt:3-12`). |
| A saved INT8 quantization report records an 18,904-byte model with input `[1,200,6]`, output `[1,2]`, and test sensitivity 0.8743 / AUC 0.8717. | **Stored artifact result, not device validation.** State the same report's threshold (0.3919), test set (6,712 windows), specificity (0.7014), and that its flash comparison is model-file size against a target—not a whole-firmware link/map measurement (`data/processed_sisfall/model/quantization_report.txt:4-33`). |
| The SPARK tracker reports Intel OpenVINO laptop timings of 0.131 ms CPU, 0.200 ms GPU, and 0.383 ms NPU over 5,000 INT8 inferences. | **Historical reported benchmark.** Attribute it to the Intel Core Ultra 7 155H gateway, not the ESP32-S3; the cited evidence is narrative tracker/proposal reporting, not a raw benchmark artifact (`dev_logs/SPARK_TRACKER.md:105-110,482`; `docs/SPARK_Proposal/Chapters/chapter3_related_theory.tex:31-35`). |
| The checked-in training code is designed to keep subject groups disjoint across one train/validation/test split. | **Code-supported protocol, not cross-validation.** `GroupShuffleSplit` is used twice and explicit set-intersection assertions check subject disjointness (`training/train_cnn.py:87-114`). Call it a subject-grouped holdout; a single split is not “cross-validation.” |
| Cohort collection, physical wearable validation, and robotics evaluation are future work. | **Planned, not completed.** Nepal trials are “Not started” and gated on logger validation plus institutional approval; procurement and hardware bring-up are pending (`README.md:24,59,72,159-161`; `docs/SPARK_POST_BOARDS_MASTER_PLAN.md:99-121`). Robotics is designated a future/exploratory extension (`docs/SPARK_Proposal/Chapters/chapter6_expected_output.tex:50-55`). |

## Rejected or unsupported thesis claims

| Claim to remove or rewrite | Why it is not supported |
|---|---|
| “At least 90% sensitivity achieved.” | The saved report gives 87.81%; the separate October log gives 89.81% at its safety threshold, still below 90% (`data/processed_sisfall/model/test_report.txt:8-12`; `training/colab_run_output.txt:145-159`). |
| A single final score/threshold/model can combine the archived reports and October run. | Provenance conflicts: archived test report/quantization report use 6,712 test windows, threshold 0.3919, AUC 0.9185, and a 18,904-byte INT8 file (`data/processed_sisfall/model/test_report.txt:3-12`; `data/processed_sisfall/model/quantization_report.txt:6,13,24-33`); the October 12 log records 38,426 windows, split 31,714/3,005/3,707, threshold 0.4236, sensitivity 0.8981, AUC 0.9272, and 18,912 bytes (`training/colab_run_output.txt:3,37-41,145-159,183`). `model_config.json` and the checked-in model header instead say threshold 0.4065 (`data/processed_sisfall/model/model_config.json:3,22-26`; `firmware/main/models/spark_cnn_int8.h:3,1588`). Do not combine these as one run absent matching model hashes, split/seed, and threshold provenance. |
| “200 Hz, 3-second window, 200 samples.” | These numbers contradict each other and the executable preprocessing. The processing script resamples to 100 Hz and creates 200-sample (2-second) windows; the 200 Hz logger is a separate planned acquisition path. A 3-second window at 200 Hz would contain 600 samples, not 200 (`training/data_prep/prepare_sisfall.py:8-14,26-32,206-207`; `AGENT.md:11`; stale tracker wording at `dev_logs/SPARK_TRACKER.md:350,725`). |
| The 80/10/10 training proportions are the realized window proportions, or the evaluation is cross-validation. | The source requests group-based split fractions, but `GroupShuffleSplit` selects groups, not exact window counts, and does not stratify by class; the saved October counts correspond to about 82.5%/7.8%/9.6% by windows. Report the actual counts and split identity rather than presenting nominal fractions as observed (`training/train_cnn.py:60-62,87-114`; `training/colab_run_output.txt:39-41`). The separate 6,712-window test report is another split/generation (`data/processed_sisfall/model/test_report.txt:3-4`). |
| Firmware performs real IMU acquisition, runs the embedded INT8 CNN, or has proven on-device fall detection/latency. | The MPU6050 implementation explicitly returns a zeroed sample without I²C (`firmware/main/drivers/mpu6050.cpp:1-31`); inference returns fixed 0.5/0.5 probabilities and constructs no TFLM interpreter (`firmware/main/tflite/inference.cpp:1-38`; `firmware/main/CMakeLists.txt:17-20`). `app_main.cpp` reads one sample, passes an all-zero `InferenceInput`, and the logger loop breaks after one sample (`firmware/main/app_main.cpp:25-45,60-75`). These are stubs/skeleton paths, not a functioning 200 Hz acquisition or inference pipeline. This conflicts with feasibility/methodology prose claiming all subsystems hardware-verified and GPIO latency verified (`docs/SPARK_Proposal/Chapters/chapter4_feasibility_study.tex:9`; `docs/SPARK_Proposal/Chapters/chapter5_methodology.tex:288`) and is contradicted by the pending hardware status (`README.md:159-160`). |
| The stated test count establishes current, hardware-verified system readiness. | Proposal prose says 48 tests passed (`docs/SPARK_Proposal/Chapters/chapter4_feasibility_study.tex:9,24`), while tracker snapshots report 48 and later 56 (`dev_logs/SPARK_TRACKER.md:32,55,82,100`). These are historical software-test counts that vary by snapshot; neither demonstrates physical hardware validation. Keep counts dated and scoped to host/software tests. |
| Nepal cohort data/results or clinical validation already exist. | The sources reviewed say trials have not started and require institutional approval and validated logging (`README.md:59,72`; `docs/SPARK_POST_BOARDS_MASTER_PLAN.md:99,115-121`). Proposal passages describing the cohort as recorded or presenting transfer learning as completed should be changed to planned protocol/work (`docs/SPARK_Proposal/Chapters/chapter5_methodology.tex:199,229-242`; `docs/SPARK_Proposal/Chapters/chapter6_expected_output.tex:23`). |
| Battery runtime/current values are measured system results. | They are explicitly estimates: methodology says no power-rail telemetry is used and labels 110–140 mA / 8–10 h unmeasured (`docs/SPARK_Proposal/Chapters/chapter5_methodology.tex:77`); the tracker likewise says no INA219 telemetry or physical profiling (`dev_logs/SPARK_TRACKER.md:518-520,841-843`). Proposal text also gives 90–130 mA / 8–11 h and event-gated 35–60 mA / 16–28 h (`docs/SPARK_Proposal/Chapters/chapter3_related_theory.tex:47`; `docs/SPARK_Proposal/Chapters/chapter4_feasibility_study.tex:15`), without measured mode-specific current or a reconciled derivation. Keep these as estimates with assumptions, not operational performance. |

## Unresolved risks before thesis freeze

1. **Split/reproducibility:** Preserve the exact subject IDs per split, seed, preprocessing version, class counts per split, and artifact hashes for each run. Current code has subject-disjoint assertions, but the saved reports do not identify the held-out subject IDs; window-level proportions differ from nominal group fractions (`training/train_cnn.py:87-114`; `training/colab_run_output.txt:39-41`; `data/processed_sisfall/model/test_report.txt:3-4`). Do not describe the single holdout as cross-validation.
2. **Threshold and model identity:** Reconcile 0.3919, 0.4236, and 0.4065 before naming a deployable threshold. In particular, the October log’s 0.4236 differs from both `model_config.json` and the embedded header at 0.4065; the older quantization report uses 0.3919. No source checked ties all three thresholds, score sets, and binary artifacts to one immutable model generation (`training/colab_run_output.txt:145-147`; `data/processed_sisfall/model/model_config.json:3,22-26`; `data/processed_sisfall/model/quantization_report.txt:13`; `firmware/main/models/spark_cnn_int8.h:3,1588`).
3. **Sampling, timing, and firmware contract:** Keep the current evaluated 100 Hz / 200-sample / 2-second model separate from the planned 200 Hz logger. Do not claim firmware conformance until the driver produces timestamped sensor samples continuously, a rolling window fills the declared 200×6 input, and a real TFLM invocation is linked and tested (`training/data_prep/prepare_sisfall.py:8-14,26-32`; `firmware/main/tflite/inference.h:21-23,49-50`; `firmware/main/drivers/mpu6050.cpp:21-31`; `firmware/main/app_main.cpp:40-45,60-75`). |
4. **Power evidence:** Record measured current by operating mode, battery/usable capacity, sampling/BLE duty cycle, and runtime on the actual device before replacing estimates with results. The existing values vary by document and mode, and no telemetry evidence is present (`docs/SPARK_Proposal/Chapters/chapter3_related_theory.tex:47`; `docs/SPARK_Proposal/Chapters/chapter5_methodology.tex:77`; `dev_logs/SPARK_TRACKER.md:518-520,841-843`). |
5. **Scope/status control:** Keep human fall detection as the evaluated thesis objective. Describe robotics, the Nepal cohort, and integrated hardware as planned extensions until their approval, collection, and device-evaluation evidence exists (`README.md:5,59,72,159-161`; `docs/SPARK_Proposal/Chapters/chapter6_expected_output.tex:50-55`). |

**Bottom line:** defensible thesis evidence is a saved, subject-grouped SisFall offline benchmark with results below the stated 90% target. The repository does not yet establish one reconciled final model result, real ESP32-S3 inference, hardware latency/power, Nepal cohort performance, or robotics deployment.
